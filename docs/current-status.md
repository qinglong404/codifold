# 当前状态与未解决的问题

Codifold 目前是 **0.1.0 初期 Demo**。开源的目的是公开工具、记录实验和积累案例，尚未形成可靠的“陌生源码项目 → 清晰逻辑图”通用方法。

## 已有的工具能力

- 读取、校验和编辑人或外部 AI 编写的工作区 JSON。
- 自动布局流程块，表达分支、循环回指、异常结构、事件和跨视图导航。
- 将逻辑块与源码行关联，提供代码对照、行映射覆盖检查和视图连贯性检查。
- 用 CLI / MCP 编译局部草稿、写入视图、检查工作区、导出 Markdown。

这些能力说明工具能够承载逻辑图，不代表它能自行理解一个陌生项目。

## 仍然没有解决的核心问题

### 1. 如何提取恰当的逻辑

陌生项目的入口、边界、隐含状态、动态分发和异常路径可能很难识别。把函数逐个翻译成中文，并不能自然得到一条读者能理解的主线。

目前还没有经过足够案例验证的分层与抽象方法。纯 AI 转换的效果不稳定；文档中的规则和任务书是实验材料，不是可靠性承诺。

### 2. 如何判断图真的有用

结构校验、100% 行映射覆盖率和 1.0000 连贯性只能检查机械条件。它们不能证明描述正确、重要路径没有遗漏、粒度合适，或新读者已经理解了程序。

现有 `gradebook`、`gradebook-chain`、`taskflow` 用来展示功能和校验规则。它们尚不足以证明方法适用于陌生项目，也不应包装成已经验证的普遍成功案例。`gradebook` 故意保留不完整映射，供教学对照。

### 3. 如何随着代码持续更新

源码映射目前以文件和行号为主，没有记录转换时的源码指纹。源码修改后，行号可能仍合法而含义已经改变；当前校验不能可靠检测这种过期。边写代码边画图时，需要在每个阶段主动对照源码复核，并记录对应提交。

### 4. 使用范围和兼容性

- 大项目的布局性能、信息密度和导航体验还没有系统验证；单视图目前最多 300 块、嵌套最多 5 层。
- 尚无完整的浏览器交互回归测试；跨平台验证依赖 CI，不能替代实际使用反馈。
- JSON 格式仍在演进，尚无正式迁移工具和稳定兼容承诺。升级前保留工作区备份。
- 工作区锁协调使用同一状态目录的 Codifold HTTP、CLI 和 MCP 写入。外部编辑器、不同状态目录的进程及网络文件系统不属于已经验证的并发场景；批量写入也不具备断电后的事务恢复能力。

## 接下来采用的探索方式

1. 自己编写边界明确的小项目，边实现边维护逻辑图。
2. 每次只整理一条具体入口或使用场景，先让这条链路讲清楚。
3. 记录源码、逻辑图、取舍、失败画法、修改经过和读者反馈。
4. 用阅读任务验证效果：读者能否解释输入输出、状态变化、分支和异常，并定位到实现。
5. 积累多个成功案例后，比较哪些规律能够复用、哪些只适用于特定场景。
6. 再把经过验证的规律提炼成 SKILL，用新的陌生项目检验它。

当前不把“自动转换所有项目”或“立即产出通用 SKILL”作为已完成能力。案例记录使用 [案例模板](case-study-template.md)，旧的转换指南保留作实验参考。

## 这轮开源整理修复了什么

- 统一版本号并把成熟度改为 Alpha / Demo。
- 把前端、示例和 MCP 指南纳入安装包，提供安装后的启动入口。
- 将最近记录与锁文件放到用户状态目录，兼容读取旧仓库记录。
- 串行化同一工作区的写入，防止两个 Codifold 写入者同时通过修订检查后互相覆盖。
- 保存与最终检查共用校验来源：契约、引用错误阻止保存；未接通的视图可作为草稿保存并返回警告，严格提交仍要求完整检查通过。
- 撤掉整目录删除功能，保留移除最近记录，避免删除与工作区放在一起的源码。
- 增加并发、校验回滚、安装包和跨平台 CI 验证。
